## Why this sprint exists

The rebuild is verified by **differential diffing against the current engine**. That makes the current engine an instrument, and an instrument has to be trustworthy before you measure with it.

**S4 made the *measuring apparatus* trustworthy. S5 makes the *subject* trustworthy.** Every task here removes a wrong answer from the reference — because a diff against an engine carrying a known wrong answer does not catch that answer, it certifies it.

**The test that decides what belongs here, and it has been applied consistently:** does the engine give a **wrong answer** the differential diff would certify, or does it simply **not model** something? A wrong answer gets repaired now. A gap gets recorded as `UNSUPPORTED` in task 5 (retired from `UNREPRESENTABLE`, task 4.3, 2026-09-14) and left for the new engine to satisfy — implementing it in an engine about to be replaced means implementing it twice. That test is what deferred withholding and capital-gain character to S103, and the property-tax model with them.

**Nothing here wires a feature.** Wiring `debt-revolving.js` into `projectDebts()`, or surfacing refinance/ARM/recast in the UI, means building a feature into an engine about to be replaced. Those move to S103+. This sprint fixes the *defects* those wirings would have exposed, and stops there.

## The sprint's defining discipline: **predict the diff before you run it**

Every task in this sprint that moves financial output runs through **S4 task 7's differential harness**, and the rule is the same for all of them:

> **Write down what you expect to move, and by roughly how much, before regenerating. An unpredicted movement is a finding — not a result to accept.**

This is not new; S5's old task 8 already carried it. Generalising it to every task is what makes the whole sprint double as the harness's proving ground. A harness proved only against a deliberately-injected fault has been tested against the one failure someone thought of. A harness that correctly predicts fifteen real changes has been tested against the ones nobody thought of.

**Task 1 is deliberately the opener because its predicted diff is empty.** It is the cheapest possible calibration of the instrument.

### 2d — Q45: a negative cross-asset correlation silently yields a **zero-volatility** portfolio

*Filed 2026-09-11, status **OPEN**. Found by sweeping the three specification documents against sprint coverage — `MARKET` P1 asks for a positive-semidefinite correlation matrix, and checking whether that was handled found a different route to the same failure in shipped code.*

`accountVolatility()` (`src/engine.js`, re-locate by symbol) models cross-asset correlation as **one scalar on every off-diagonal pair**. That is an equicorrelation matrix, positive semidefinite only for **rho ≥ −1/(n−1)**. Below the floor the variance goes negative and `Math.max(0, variance)` silently clamps it to zero. Neither `app-shell.html:324` (`min="-1" max="1"`) nor `scenario-validator.js:628` (`checkRange(…, -1, 1)`) knows how many asset classes exist.

**Measured by executing the shipped function, not by reading it.** At the default three classes the floor is −0.5, and a conservative **20/50/30 allocation at rho = −1 has exactly 0.0000% volatility.** The sharper case is that asset classes are user-editable and the floor *rises* with n: at **five classes, rho = −0.3 gives 0.000%** — which is what someone types when they believe their holdings are diversified, not an adversarial input.

**The error direction is the dangerous one.** A zero-volatility portfolio has no downside sequence, so every Monte Carlo path is the mean path and the success rate goes to ~100%. It **overstates** the plan's safety.

**And the band above the clamp is worse than the clamp.** Between the PSD floor and the point where variance goes negative, the engine returns a **finite, plausible-looking volatility from a mathematically invalid matrix** — no clamp, no warning. That is FC-02's shape: a finite wrong answer is harder to catch than an infinite one.
