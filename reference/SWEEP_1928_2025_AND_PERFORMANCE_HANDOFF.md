## Part 1: the sweep and what it found

After the M5.1R reserve-emergency fix was verified (see `RESERVE_EMERGENCY_LOCKUP_HANDOFF.md` in this same folder), every valid historical start year from 1928 through 2025 was run through the fixed engine — 98 windows total, each `min(55, 2025 - start_year + 1)` years long (a full 55-year window where the data allows, shrinking near the 2025 data boundary).

Result: **91 passed clean, 1 failed correctly (1929 — genuine Depression-era portfolio exhaustion, not a bug, already covered in the reserve-emergency handoff), and 6 crashed with an unhandled exception**: start years 1935, 1956, 1957, 1961, 1989, 1999, all with `ValueError: Social Security claim-age state fields disagree`.

**That crash is filed in full detail, with root cause traced to `simulation_engine.py:656-657` and `social_security_state.py:95-107`, in a separate document: `SS_CLAIM_AGE_MONTHS_CRASH_HANDOFF.md` in this same folder — read that one for the actual defect.** This document doesn't repeat that analysis; it's here for the sweep methodology and the performance work below.

**Why a single-window formal run (M5.1, M5.1R) never caught this:** 1971 is the only historical window that has ever been formally run under this project's release process, and its Social Security claim happened to land on an exact 12-month boundary by chance of that specific historical return sequence. A single canonical window is not sufficient evidence that the engine behaves correctly across the input space it claims to support — the crash rate here was 6/98 (~6%) and spans unrelated historical eras (Depression-era through modern), meaning it's a systemic timing-alignment issue reachable by ordinary input variation, not a contrived adversarial case.

**Recommendation:** consider whether a broad historical sweep (or at least a handful of start years beyond 1971) belongs somewhere in the regular validation process for future changes to Social Security claim-timing logic, given a single window already proved insufficient to catch a defect that hits 1 in ~16 valid inputs.

## Part 2: running this sweep fast, without touching the engine

The first (correct) attempt at this sweep took **1086 seconds (~18 minutes)** run sequentially, one window after another in a single process. Two things were done to make this faster — both are pure orchestration changes with zero effect on what gets computed, and both are safe to reuse for any future sweep-style validation work.

### A latent API footgun found and worked around (not a financial-logic bug, but worth fixing)

`ModularRetirementModel.run_window()` does not reset `self.diagnostics` between calls on the same instance — `DiagnosticSuite`/`DiagnosticsReport` is constructed once in `__init__` (`simulation_engine.py:109`) and never replaced or cleared inside `run_window`. The first version of the sweep script reused one model instance across all 98 windows for efficiency and got corrupted results as a consequence: a 6-year window run immediately after a 55-year window with 56 diagnostic errors inherited those same 56 errors, even though the 6-year window was actually clean. This was caught before any conclusions were drawn from it (a control check on a short window unexpectedly showed the same error count as the immediately preceding window, which was the tell), by verifying: constructing a **fresh model per window** (while still sharing the read-only `config`/`repository` objects, which cost ~74ms combined to build and don't need per-window reconstruction) produces the correct independent-per-window diagnostics.

This is not itself a defect in the shipped product (`run_simulation.py` always builds exactly one model per process and calls `run_window` exactly once, so it can never manifest there), but it will silently corrupt results for anyone — including future automated validation tooling — who reuses a model instance across multiple `run_window` calls expecting independent diagnostics each time. Worth either resetting `self.diagnostics = DiagnosticSuite(diagnostics_cfg)` at the top of `run_window`, or documenting explicitly that a model instance is single-use per window.

### The actual speedup: process-level parallelism (11x, verified bit-identical)

Every historical window is a fully independent computation — nothing about window A's result depends on window B. This machine has 32 CPU cores, so the 98 windows were distributed across 24 worker processes (`concurrent.futures.ProcessPoolExecutor`), each worker building its own model from shared `config`/`repository` objects and computing its assigned windows exactly as the sequential version did.

**Result: 1086s -> 100s (10.9x wall-clock speedup).** Before trusting this, every field of every one of the 98 results (diagnostics passed/errors/warnings/issue codes, effectiveness classification and score, ending real total, and exception messages for the 6 crashing windows) was diffed between the sequential run and the parallel run: **zero mismatches.** The parallel version is not an approximation — it is the same computation, run concurrently.

This pattern (fresh model per window, shared read-only config/repository, `ProcessPoolExecutor` across independent windows) is safe to reuse for any future sweep-style validation across historical windows, sensitivity grids, or adversarial fixtures, without needing to touch or re-certify the underlying financial engine.

### What the profile shows the time is actually going to

`cProfile` on a single 55-year window (1971) shows the Social Security optimizer's own designed search dominates runtime: roughly 50 candidate claim-months (one-month granularity across the eligible range) x 3 configured economic planning scenarios (`config["planning_scenarios"]` — different assumed future return/inflation/income-growth paths, not mortality alternatives; mortality-alternative sensitivity is a separate, smaller pass counted in the `ss_evaluations`/`ss_sensitivity_flips` diagnostics counters) x ~53 remaining projected years per SS-eligible decision year. That adds up to **1,189,250 `tax_engine.calculate()` calls in one 55-year window — about 92% of total runtime.** That is accuracy-critical financial logic and was not touched or second-guessed for its economic content — per this project's own priority order (`AGENTS.md` §4: correctness -> reproducibility -> stability -> validation -> profiling -> optimization), changing what the SS search actually computes needs a dedicated, gated R3/R4 task, not an incidental change.

Separately from that core computation, the same profile shows a meaningful amount of **pure Python/mechanical overhead unrelated to the financial math**: `builtins.max` called 38,016,459 times (3.858s), `dataclasses.replace()` called 602,258 times (2.119s), and `float()` coercion going through the slow abstract `numbers.Real.__float__` dispatch path 5,902,957 times (2.697s) rather than a direct builtin float conversion. Together this is roughly 10% of total runtime that is implementation overhead, not computation — a candidate area to look at if/when a dedicated performance task is ever opened. This is a lead, not a recommendation to act now.

### The second verified speedup: memoizing the pure tax calculation (1.4x, stacks with parallelism)

Reading `social_security_valuation.py:340-366` (`_projected_incremental_tax_real`) closely: for each candidate claim-month, it computes a "without-benefit" baseline tax and a "with-benefit" tax, and returns their difference. The **baseline half is candidate-invariant** — it depends only on `(planning_state, scenario, projection_year)`, never on which claim-month candidate is being scored — yet it is recomputed fresh for every one of the ~50 candidates compared per decision year, when only 3 scenarios x ~53 years = 159 truly distinct baseline cases exist per decision year. That is up to ~50x redundant recomputation of an identical, pure calculation.

**Verified this is safe to cache, then verified the result is unaffected, both empirically:**
1. Confirmed `TaxCalculator.calculate()` (`tax_engine.py:41`) has no side effects — it only reads `self.config` (fixed for the object's lifetime) and its two arguments, and returns a new `TaxResult`. No mutation, no logging, no randomness.
2. Confirmed `TaxIncome` (`model_types.py:122`) is a frozen, all-float dataclass — hashable, so its instances are safe to use directly as cache keys.
3. Wrapped `TaxCalculator.calculate` externally with a memoizing cache keyed on `(id(self), income, inflation_factor)` (a monkeypatch — no source file was changed) and ran the real 1971/55 window with and without it.
4. **Result: 1,155,019 cache hits out of 1,189,250 calls (97.1% hit rate) — the true redundancy is even higher than the "candidate-invariant half" estimate above, likely because other call sites (bridge opportunity-cost projections, reserve-refill exploration) redundantly repeat identical `(income, inflation_factor)` pairs too.** Elapsed time for the window dropped from 12.9s to 9.0s — a **1.43x speedup**.
5. **Verified the result is unaffected**, and did not take a first "looks equal" pass at face value: an initial whole-dict equality check returned `False`, which was chased down rather than dismissed. The first cause found was a harmless mismatch in the demo script's own `run_id` label between the two runs (cosmetic, not a computation difference) — fixed and rechecked. A second, full recursive field-by-field diff then found the *only* remaining differences were in `diagnostics.timings_ms` (wall-clock instrumentation that is expected to vary between runs, same category already established as noise in prior determinism checks — see `RESERVE_EMERGENCY_LOCKUP_HANDOFF.md`'s determinism section). Every annual financial value, diagnostic issue, counter, and the effectiveness grade were bit-identical.

This stacks multiplicatively with the process-parallelism result above. **This finding is superseded by a fuller investigation below — read that section for the complete, more accurate picture** — but it's left here because it was the first thread pulled and the deeper investigation confirms and extends it rather than contradicting it.

### Part 3: is a faster *search* possible? Investigated deeply (Opus), independently spot-checked (Sonnet) — no, but a much faster *evaluation* is, and it's proven across 10 full historical windows

The finding above only cached one redundant sub-computation inside the existing brute-force candidate grid. The natural next question is bigger: **can the search itself be smarter than brute force?** If the economic value of claiming Social Security were a smooth, single-peaked function of claim-month, a binary/ternary/golden-section search could find the same optimal candidate in ~7 evaluations instead of ~50-97 — a much larger win than caching alone. This was investigated rigorously (an Opus pass, with one core claim independently re-verified against the actual source by a second, separate reading) rather than assumed, because getting this wrong would silently change which claim-month gets selected — exactly the kind of accuracy sacrifice that's off the table.

**Verdict: no faster search is possible, for two independent reasons, both proven empirically — but a much faster *evaluation* of the existing exhaustive grid is possible, and it was verified end-to-end (full result payload and full decision log, byte-for-byte, via SHA-256) across 10 complete historical windows spanning 1928-1999.**

**Reason 1 — the objective is not unimodal.** The full candidate grid (all ~97 months) was brute-force evaluated at 116 real decision points pulled from 12 different historical windows (portfolios ranging $110K-$2.4M, ages and market conditions varied deliberately toward edge cases). **36.5% of grids (38 of 104 non-degenerate cases) have multiple strict local maxima in net economic value — up to 7 in one case** (a 1946-start window's 1963 decision: peaks at claim-months 746, 758, 778, 784, 796, 808, and 821). A concrete counterexample from a 1971-start window's 1988 decision: net economic value rises to $172,737.42 at month 766, *falls* to $172,670.40 at month 768, rises again to $178,461.53 at month 802, falls to $178,360.11 at month 804, then rises to the true global maximum at month 826. These dips are ~4 orders of magnitude larger than floating-point noise — a real structural feature, not numerical jitter. The cause is traced to the delayed-retirement-credit schedule's January-aligned deferral logic combined with `projection_year = offset_months // 12` bucketing, which puts a kink at every attained-age year boundary — this isn't a quirk of one scenario, it will recur in any window.

**Reason 2 (more decisive, and the one independently re-verified) — the winner isn't even the argmax of economic value.** `_select_candidate` (`social_security_optimizer.py:461`) doesn't just pick the best-economic-value candidate. It applies, in order: (1) a floor-depletion filter, (2) a robustness/acceptability-rate filter (whose threshold depends on the *global* best rate across all candidates), (3) an economic "close pool" — candidates within `economic_close_call_fraction` of the *global* best economic value (this step alone requires having computed the full grid's maximum first, so nothing before this point can be skipped), and only then (4) a **lexicographic tiebreak on longevity/robustness fields** (`depletion_protection`, `minimum_checkpoint_coverage`, `reserve_equivalent_real`, `-conditional_shortfall_pv`, ...) — not on economic value at all. Independently confirmed by reading `_select_candidate` directly: this is exactly right. Across the 104 test grids, the pure economic argmax was the actual winner in **zero of them**. The "close pool" that actually matters for the final decision averaged 73% of the entire grid (range 32%-100%). There is no way to shortcut a search whose own selection rule requires the full grid's maximum and a close-enough band around it just to define which candidates are even in contention.

**What is possible: eliminate redundant work within the (unavoidable) full grid evaluation, proven exact.** Four layered, purely operation-preserving changes, each verified to produce bit-identical output:

| Layer | What it does | Cumulative speedup |
|---|---|---|
| P4 | Hoist loop-invariant `Fraction`->`float` conversions in the per-mortality-point longevity loop out of the hot path (pure code motion, no numeric change) | 1.115x |
| P5 | Index survival-curve points directly instead of scanning with `continue`; share the pre-claim balance prefix across candidates (bit-exact because pre-claim benefits are always `0.0`) | 1.144x |
| P2 | Memoize `TaxCalculator.calculate` (the finding above, refined: the redundancy is invariant to mortality alternative *and* both scenario return assumptions, not just the "without-benefit" half) | 1.699x |
| **P1** | **Memoize `_evaluate_scenario` itself** on its true numeric dependencies (not the whole `PlanningScenario` object, since the sensitivity passes vary only `real_portfolio_return`, making the lower/higher-return sensitivity grids collapse to scenarios numerically identical to ones already computed in the central grid — 28.6% of all `_evaluate_scenario` calls, 7,938 of 27,783, are exact duplicates) | **2.325x** |

Full validation, not a spot check: **10 complete historical windows (1928, 1946, 1964, 1971, 1995, plus 5 more spanning to 1999), each run start-to-finish twice — once unpatched, once with all four layers — and the *entire* result payload plus *every single decision-log line* (2,983 lines total across the 10 windows) hashed with SHA-256 and compared. All matched exactly** (only `timings_ms`, wall-clock instrumentation, was excluded, consistent with every prior determinism check in this project). Per-window speedup ranged 1.86x-2.42x; **2.20x averaged across all 10 windows combined (135.0s -> 61.3s)**.

**Combined with process-level parallelism — actually run, not estimated:** the full 98-window sweep was rerun with parallelism (24 workers) and all four evaluation layers active together, fresh per window. **1086s -> 49.3s, a measured 22.0x**, with every field of every one of the 98 results re-diffed against the original sequential baseline: zero mismatches. This supersedes the earlier ~24x multiplicative estimate with a real number.

**What was tried and explicitly rejected, with reasons (saves re-deriving these):**
- Ternary/golden-section/derivative search on claim-month — disproven twice over, above.
- A coarse-then-fine grid (the pattern already used by the *other* optimizer in this codebase, `lifetime_tax_optimizer.py`'s `coarse_mix_step`/`fine_mix_step`) — inapplicable here specifically because it would prune candidates before the acceptability-rate and close-pool filters see them, changing which candidates are even eligible for the tiebreak, not just how fast the answer is found.
- A mortality-profile-level memo — real but negligible (85.7% hit rate, ~0% time savings; profile construction is already cheap).
- Dynamic-programming reuse of the delay-bridge opportunity-cost projection across neighboring candidates — investigated and traced, but the bridge's funding-source ranking depends on claim-month through a term that isn't provably rank-stable across candidates without a per-run proof; the bridge is only ~10% of post-memoization time, judged not worth the correctness risk.
- Vectorizing the year/month loops with numpy — the remaining hot spots are diffuse Python/interpreter overhead (dict lookups, `dataclasses.replace`, generator expressions) rather than one obvious inner loop, and any reassociation of floating-point operations risks violating this project's own `REQ-DET-001` exact-determinism requirement. Not recommended.

**Validation protocol recommended for Codex if this is implemented for real:** run at least 10 window starts spanning 1928-1999 (the same set used above is a reasonable starting point), hash the complete `result.to_dict()` and every decision-log line before and after the change (excluding only `timings_ms`), and require exact equality — not a tolerance-based comparison, since every change proposed here is claimed to be exactly identical, so any drift at all indicates a real bug. Also worth a targeted unit test asserting that `_evaluate_scenario` returns results differing only in their `.scenario`/`.longevity.scenario` label field for two `PlanningScenario` inputs that are numerically identical but differently named (this is the exact mechanism P1 relies on).

**Incidental, not new:** this investigation also independently reproduced `run_window(1999, 27)` crashing with the same `ValueError: Social Security claim-age state fields disagree` already filed in `SS_CLAIM_AGE_MONTHS_CRASH_HANDOFF.md` (1999 is one of the 6 known-crashing start years from the Part 1 sweep, at its natural `min(55, 2025-1999+1)=27`-year horizon) — this is confirmation of the existing filed defect, not a new one. Additional data point gathered in passing: `1998+27`, `1997+28`, `1990+27`, and `1970+26/27/28` all pass, consistent with the existing root-cause finding that this is specific to whether a given window's optimal claim month happens to land on a non-12-multiple, not a general property of 27-year windows.
